# Portable backup and restore

[Start here](../README.md) · [Server startup](server-startup.md) · [Database schema](database-schema.md) · [Testing](testing.md#backup-and-recovery-validation)

## Status and scope

**Portable backup and offline recovery are implemented, with an isolated selected-revision recovery walkthrough.** Knowledge-database WAL startup, canonical codecs/compiled inventory, online capture/Git delivery, source-aware whole attempts, configured daemon scheduling, the manual backup command, immutable historical fences, private staging/recovery and empty-destination restore are implemented. The standalone restore command selects an existing local snapshot; it never fetches a revision or calls a native service. See [validation evidence and limits](testing.md#selected-revision-recovery-walkthrough). Current stopped-file copies have a separate [limited procedure](server-startup.md#paired-media-backup-and-restore).

This is disaster recovery: versioned JSON plus byte-exact retained image/PDF originals, preserving identities and relationships, including rejected material. Capture must work while the daemon serves requests. Restore is a standalone, offline operation into an empty installation, not an HTTP route, editable-file interface, import/merge operation or native-service backup. A dedicated ordinary Git repository is the destination; GitHub is expected, a private repository is strongly recommended. Repository/account creation and remote administration remain operator work.

## Privacy and trust

- Backups are **readable, not encrypted**. They contain rejected thoughts, replies, conversations, original Markdown bytes, image/PDF files, filenames, provenance, request keys and private prepared prompts. Git history can retain content subsequently deleted from the application. Local deletion is not backup or provider erasure.
- Historical bindings retain endpoint, model, permissions, workspace paths and native IDs; execution-owner records retain historical path/device/inode identity. These are durable facts, not a copy of host configuration or permission to use that endpoint. Prepared prompts can contain old absolute media paths. Do not redact or rewrite them and call the result lossless.
- Exclude `.env`, bearer/provider credentials, private launchers, agent configuration, host Git/SSH credentials, logs, source checkouts and OpenCode-owned sessions/databases/files. Host-managed Git authentication stays outside the payload. Content can itself contain a user-entered secret; exclusion of configuration is not content secret-scanning.
- SHA-256 detects corruption and inconsistent files, **not a malicious replacement of both data and hashes**. The operator selects a trusted repository/revision independently. Restore never executes snapshot SQL, code, hooks, filters, links or embedded instructions.

## Version 1 payload

One Git revision contains one complete `snapshot/` tree. Previous revisions are its history; do not accumulate timestamp-named copies within that tree.

```text
snapshot/
  manifest.json
  tables/<table-name>.json
  media/store.json                 # absent only when SQL media_store is empty
  media/objects/<source-id>        # one original per media_sources row
```

No SQLite database, WAL, journal, SHM or execution-owner sidecar belongs in this tree. No filesystem staging, prepared media scratch, unreferenced object or empty-directory placeholder belongs in it. Identical original bytes belonging to distinct source IDs remain distinct object entries. Original filenames are display metadata, never storage paths.

### Manifest

`manifest.json` has exactly these keys:

| Key | Value |
| --- | --- |
| `format` | `"thoughtloom-backup"`. |
| `version` | JSON integer `1`, the envelope/encoding version. |
| `appSchema` | `"thoughtloom-logical-1"`, the explicitly supported application-table contract described below, including the restore-fence metadata table. This is not SQLite's `schema_version` or a service version. |
| `mediaStoreId` | Exact SQL `media_store.store_id`, or null when that table is empty. |
| `tables` | Entries sorted by table name: exact `{name,path,rowCount,byteLength,sha256}` for every included table, even an empty one. |
| `sequences` | Entries sorted by name: exact `{name,value}` for `sqlite_sequence` high-water values of `import_documents`, `markdown_imports` and `search_sessions`. Omit an entry only if SQLite has no entry for that table. `value` uses the integer cell encoding below. |
| `mediaMarker` | Null, or exact `{path,byteLength,sha256}` for `media/store.json`. |
| `originals` | Entries sorted by source ID: exact `{sourceId,path,byteLength,sha256}` for every snapshotted media source. |

Counts and byte lengths are canonical nonnegative decimal **strings**, without signs or leading zeroes except `"0"`. Hashes are 64 lowercase hexadecimal SHA-256 characters over actual file bytes. Table paths are exactly `tables/<name>.json`; object paths exactly `media/objects/<sourceId>`. Manifest object entries must agree with SQL source IDs, lengths and binary digests. The marker is canonical `{"version":1,"storeId":"<exact-id>"}` plus LF, reconstructed from the validated identity rather than copied with arbitrary marker formatting. Null identity requires no sources, marker or objects.

The SHA-256 of the canonical manifest bytes identifies the snapshot; it is not stored recursively in itself. Capture times, attempt IDs, host paths, wall-clock schedule state and Git delivery results are **not** payload fields. Log them separately. Unchanged logical data, identities, relevant ordering and sequence values produce identical bytes and no new Git commit.

### Table files and exact scalar encoding

Each table file has exactly `{columns,rows}`. `columns` is the supported column-name list sorted in ASCII order, not source DDL order. Each row is exactly `{rowid,values}`; `values` matches that list. `rowid` is null except for the ordering-sensitive tables identified below, where it uses the integer encoding. No missing fields, omitted nulls or extra columns are allowed.

| SQLite storage class | JSON cell |
| --- | --- |
| NULL | `null` |
| TEXT | A JSON string, with its exact Unicode content, including leading U+FEFF, whitespace, line endings and embedded JSON-as-text. Never parse/reformat stored JSON text as part of backup. |
| INTEGER | `{"$integer":"-123"}`; canonical signed decimal, no `+`, leading zeroes or `-0`, within signed 64-bit range. This also encodes booleans stored as integers. |
| BLOB | `{"$blob":"AAE="}`; standard padded RFC 4648 base64, verified by decode/re-encode equality. A digest BLOB stays binary; it is not a hex string in a table cell. |

There are no supported REAL columns. Reject an unexpected storage class or non-round-trippable TEXT rather than coercing, rounding or replacing it. Read INTEGER values with Bun's `safeIntegers: true`; do not pass them through JavaScript numbers. Read/validate exact TEXT bytes through a BLOB projection where needed, and restore TEXT using UTF-8 bytes with `CAST(? AS TEXT)`; ordinary Bun string binding can consume a leading U+FEFF. Validate SQLite constraints and application-required safe-integer ranges without truncation.

Canonical JSON uses UTF-8 without BOM, compact `JSON.stringify` string escaping, object keys in ASCII order at every structural level, and one final LF. Stored TEXT is a scalar, not a structural object. Sort rows by their declared primary key in key order (INTEGER numerically, TEXT by UTF-8 byte order, not locale); this means `sequence` for `import_documents`, `markdown_imports` and `search_sessions`. Ordering-sensitive tables instead sort by numeric preserved rowid. Do not depend on unspecified SELECT order.

Preserve implicit rowids for `runs`, `run_operation_receipts`, `response_thoughts`, `run_context`, `markdown_import_files`, `import_namespaces` and `search_native_cleanup`: worker queue order, legacy receipt order, response/context order and import/cleanup scans use them. Preserve explicit `sequence`, `position` and ordinal columns everywhere. Other implicit rowids, FTS document IDs, physical page layout and obsolete cursor signatures are not recovery identities. Preserve the listed rowids before any operation that can renumber them; UUID sorting is not a substitute for queue or association order.

The implemented internal [`format.ts`](../src/backup/format.ts) encodes raw typed cells and manifest metadata; [`decode.ts`](../src/backup/decode.ts) decodes only the complete compiled inventory and its effective storage types/nullability. Primary keys cannot be null even where SQLite reports `notnull=0` for an INTEGER PRIMARY KEY. Decoding preserves BOM text, bigint integers and binary bytes, then requires exact canonical re-encoding. Alternate escaping/whitespace, duplicate keys, wrong order, invalid UTF-8/base64 and unknown scalar/structural fields are refused. These codecs alone do not validate actual file hashes or cross-record relationships. Capture and private staging supply those separate boundaries below.

### Application schema inventory

This inventory is grounded in the migration functions and current readers, not a live/user database. Every current persistent application table is classified here. Capture and restore use a **compiled allowlist of tables, columns, keys and storage types** for `appSchema`, checked against the actual source schema. They do not dynamically export unknown tables or accept SQL definitions from the payload. Unrecognized tables/columns or incompatible definitions fail closed rather than disappearing silently. SQLite-owned derived objects are classified separately below.

| Classification | Tables | Treatment |

No AI scope filtering. |
| Durable execution history | `runs`, `run_steps`, `agent_bindings`, `run_context`, `run_operation_receipts`, `run_issued_thoughts`, `run_replies`, `execution_owners` | Include immutable IDs/inputs, envelopes, results, drafts, confirmed receipts, binding/owner attribution and actual cancellation evidence. | Export history | `export_intents`, `export_reports` | Include original requests/effort and completed reports/attribution, without making reports AI-readable knowledge. |
| Retained Markdown sources | `import_namespaces`, `import_documents`, `import_locations`, `import_document_parts`, `import_document_seals` | Include exact BLOB original bytes/digests, locators, parser/segmentation facts and complete membership maps/seals, including zero-thought documents. |

| Retained media metadata | `media_store`, `media_sources` | Include exact store identity, source/request identity, fingerprint, filename, clarification and root association, plus the referenced original files. There is no `media_files` table. |

| Recovery-control metadata | `restore_fences` | Implemented additive storage, entity-authority checks, exact original-state staging, recovery transitions and offline installation; fresh/migrated installations start empty. | SQLite bookkeeping | `sqlite_sequence`; any SQLite-owned statistics such as `sqlite_stat1`/`sqlite_stat4` | Preserve only the named AUTOINCREMENT high-water values in the manifest. Statistics are rebuildable; do not ship arbitrary `sqlite_*` records. |

| Filesystem control/scratch | `<db>.execution-owner.sqlite` and its companions, knowledge-DB companions, media `staging`/`prepared`, unreferenced objects, backup locks/workspaces | Exclude. Source anchors: [core migration](../src/storage/sqlite.ts), [run](../src/storage/run-schema.ts), [receipt](../src/storage/run-receipt-schema.ts), [export](../src/storage/agentic-export-schema.ts), [import](../src/storage/import-schema.ts), [media](../src/storage/media-schema.ts), [search](../src/storage/search-schema.ts), [cleanup](../src/storage/search-cleanup-schema.ts), and [owner registry](../src/storage/execution-owner-schema.ts). Import/search/media migrations widen the bootstrap definitions; `run-schema.ts` alone is not today's complete schema. [Media paths](../src/storage/media-file-paths.ts) and [publication/cleanup](../src/storage/media-files.ts) own the file boundary.

The implemented [`schema.ts`](../src/backup/schema.ts) checks a compiled inventory of 41 payload tables plus the excluded spelling epoch. It compares actual declared types/nullability, ordered primary/composite foreign keys and their actions, unique-key columns/collations/partial predicates, rowid-table shape and AUTOINCREMENT usage. It allows only the exact derived virtual/shadow and SQLite bookkeeping names above, not a broad FTS-name prefix. Read-only metadata inspection accepts Bun number or bigint PRAGMA results and returns frozen table shapes; capture must invoke it within its coherent source transaction. Extra non-unique performance indexes are harmless to the payload. This is not byte-for-byte validation of historical defaults, CHECK expressions, FK deferral clauses or trigger SQL, nor validation of record contents/relationships; normal application migrations and the later capture/restore invariant checks retain those responsibilities. Unsupported extra user tables are refused, even if ordinary migration correctly preserves them.

### Compatibility and evolution

The implemented codecs, inventory, private staging/recovery and installation target only `thoughtloom-logical-1`. Normal application migration adds the empty recovery-control table without changing existing data; pre-feature databases first take that migration on daemon startup. Capture must not migrate a source database. Decoding refuses unknown format versions, app-schema IDs, table/column sets and scalar tags; staging additionally validates the loaded relationships and exact re-encoded records. A newer application version is not rejected just for being newer when it still explicitly supports this contract.

Future schema changes must update the inventory, typed codec and preservation tests in the same change. Add an explicit tested adapter or a new app-schema ID; never guess missing fields or silently discard unknown history. Change the outer format version when encoding/layout semantics change. Native session/protocol versions are historical data, not a request to attach to a provider. Run ordinary supported migrations on restored data only under the offline loader/startup safety gate; never execute DDL from a manifest.

## Coherent online capture

### Internal invocation and limits

[`captureBackup(options)`](../src/backup/capture.ts) is an explicit internal Bun API, not a daemon route, startup job or installed command. Required absolute paths are `databasePath`, `mediaDirectory` and `outputDirectory`; optional fields are `signal`, an instance `logger`, and `limits`. The output parent must already exist, be owned by the current UID with mode `0700`, and be outside a Git checkout and separate from the managed media tree. Caller-owned entries in that parent are not staged or cleaned. Paths must be canonical without symlink components; existing source/storage permissions and the supported Linux local-filesystem boundary still apply. Capture acquires **no execution-owner lease**, registers no owner and initializes no media store.

The result is `{snapshotDirectory,manifestSha256}`. The selected directory is `<outputDirectory>/snapshot-<manifestSha256>` and contains the payload contents shown above, with no enclosing duplicate `snapshot/` level. The separate internal Git delivery API copies those contents under its own `snapshot/` prefix. There is no automatic retry, Git operation or background schedule in capture itself. Callers own cancellation/shutdown: abort the supplied signal and await settlement before discarding resources.

| Technical limit | Default / enforcement |
| --- | --- |
| `limits.sourceReadMs` | `10000`; the parent kills and joins the owned child if startup, the pinned-snapshot handshake, validation or raw SQL collection exceeds this deadline. |
| `limits.totalMs` | `120000`; parent cancellation covers capture and pre-publication verification. The child also has a rounded-up whole-second CPU limit through `/usr/bin/prlimit`; core dumps are disabled. |
| `limits.maxRssBytes` | `536870912` (512 MiB); parent samples the child's Linux `/proc/<pid>/status` RSS every 25 ms and kills/joins it after observing an excess. |
| Missing-RSS exit reconciliation | Fixed 100 ms, at most once per attempt, only for the complete status case below. This is not a public option or an extension of the source/total deadlines. |
| Control I/O | At most 8192 combined stdout/stderr bytes; only closed phase/count/digest messages are interpreted, and stderr is discarded without logging. Private request metadata is capped at 16 KiB. |

Limits are positive safe integers; the source deadline cannot exceed the total deadline, which must fit a JavaScript timer. These are per-attempt technical budgets, not permanent record/file-count limits or a truncation policy. RSS monitoring is **sampled**, not a hard allocation ceiling or an OOM-proof sandbox; transient peaks can exceed it, and parent scheduling can delay observation. No `RLIMIT_AS` is used: JavaScriptCore reserves substantial virtual address space. No default upload-size setting restricts retained-original backup. The child is launched with exact `bun --no-env-file` arguments, a private working directory and only fixed PATH/LANG values, never inherited credentials, private environment files or native-service configuration. Abort, timeout, control failure and resource refusal join the process, pipes and active RSS sample before attempt cleanup.

Each RSS status read is limited to 8192 bytes and 8192 read calls, assembling short reads until a numeric `VmRSS` line or EOF; a usable measurement does not require unrelated trailing fields. `ENOENT`/`ESRCH` during open/read, or missing RSS with a valid `Z`/`X` state, means no sample, not successful child exit. Without a usable measurement or terminal state, empty/truncated records and missing/invalid state remain fail-closed. Bad RSS tokens, read errors and descriptor-close errors are fatal, not eligible for reconciliation. The standalone status reader still refuses nonterminal missing RSS.

Linux can produce a complete nonterminal status without its memory section. The supervisor recognizes only an LF-terminated EOF record with exactly one `Name`, recognized `State`, matching `Pid` and numeric `nonvoluntary_ctxt_switches` base-tail field. For this case alone, it waits up to 100 ms for its **actual owned child-exit promise**, independently of delayed lifecycle/exit observation. Four ordinary sample periods allow a small kernel-teardown/notification window without permitting indefinite live work without RSS. It neither substitutes zero memory nor retries the capture/resets the window. If the child remains live, expiry immediately latches `monitor-unavailable`, kills and joins it. Abort, source/total deadlines and other failures interrupt the wait without replacing their latched reason. Timer disposal seals late callbacks on every settlement; the active reader/sample is joined before deciding success. Parent scheduling can delay this timer, so it is not a hard real-time/RSS guarantee. Successful capture still requires actual exit0, completed exit observation and valid complete phase/digest protocol; a sample never authorizes publication.

Monitor failures emit Error `[backup] RSS monitor failed` with whitelisted `stage` (`open`, `read`, `parse`, `close`, `sample`), `category` (`permission`, `io`, `resource`, `malformed`, `limit`, `unknown`) and, for classified parse refusals, optional `reason` (`missing-rss`, `invalid-rss`, `invalid-status`). These are static values, never raw exceptions, proc contents or paths. Genuine malformed/I/O refusals and previously latched memory/abort/deadline failures are not converted into success by later exit.

### SQL boundary

Daemon startup enables and verifies knowledge-database **WAL mode** under the execution-owner lease before normal migration/workers. The private execution-owner sidecar remains in `DELETE` mode with its existing lifetime exclusive transaction. Capture refuses a rollback-mode source with `wal-required`; open/migrate it through normal WAL-capable daemon startup before trying again. Capture never silently changes a running database's journal mode.

The fixed [`capture worker`](../src/backup/capture-worker.ts) uses one separate read-only Bun connection (`create:false`, `safeIntegers:true`, query-only and trusted-schema-off, with no shared-cache/read-uncommitted mode). Its one-second SQLite busy wait is still bounded by the parent's source deadline. It refuses a source with the restore-in-progress marker described below and checks canonical path/device/inode identity around operations instead of adopting a replacement. [`readSource`](../src/backup/capture-source.ts) begins one read transaction, establishes its snapshot with an actual schema read, validates the supported inventory and collects all allowlisted raw typed rows, meaningful rowids, sequence values and media identity from **that same transaction**. TEXT is selected as bytes with a separate storage-class projection; integers never pass through JavaScript numbers. It materializes raw values privately, then commits/rolls back and closes the connection **before** encoding, file hashing/copying or Git. There is no main-daemon full-data scan and no unrelated per-table transaction sequence.

Before publication, checks cover SQLite integrity/FKs, row counts/storage classes, source-list/issued/association order, required thought/response/document seals, forest ancestry, polymorphic run/search dependency references, import byte coverage/membership/locators, retained-document/pending-input SHA-256, media-root associations and search turn/discovery ownership. Later title edits are valid; validation does not replay initial admission or require imported thoughts to remain untitled. Historical nullable/unknown journal facts stay unchanged rather than being reconstructed as native proof. The capture validator is not an interpretation of arbitrary old model envelopes or a native terminal-evidence verifier.

Shared raw-record validation also applies the application's existing nonnegative safe-integer revision/cursor ranges using exact bigint comparisons (`0` through `9007199254740991`, inclusive): plural search epochs; search session revision/sequence; composer revision; search-run generation; retained-document and import-batch sequences; and preserved import-file/response-association rowids. Staging refuses out-of-range records as `invalid-records`, even when int64 encoding, hashes and SQL constraints otherwise pass. This is not a global integer limit: ordinary-run generations, manifest sequence high-water values and other supported integers retain their full int64 encoding. No extra room for a future increment is required.

The parent logs Info `source snapshot established` while the actual WAL snapshot is pinned and before authorizing its raw-row scan; `source snapshot released` follows connection close, with table/row counts. These are real bounded control events, not readiness inferred from sleep. Capture logs attempt/outcome, safe failure categories and manifest digests, not payloads, paths or raw errors. WAL permits concurrent commits; a long reader can still retain WAL pages and delay checkpoints. Owned concurrency/latency evidence must verify the configured budgets. Capture changes no business rows, generations, identities or cancellation facts.

[SQLite isolation](https://www.sqlite.org/isolation.html) establishes the read-transaction contract. [Bun SQLite](https://bun.sh/docs/runtime/sqlite) documents read-only connections and exact integers. [SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html) documents `VACUUM INTO` as a consistent live snapshot and explicitly **not** a source write operation, but also warns that VACUUM may change implicit rowids. It is not the chosen capture mechanism. Neither an unguarded live DB/WAL copy nor a copy of the execution-owner sidecar establishes a logical snapshot. A different snapshot primitive needs explicit rowid/concurrency proof before substituting it.

### Original-file boundary

Capture uses the **snapshotted** `media_sources` list/fingerprints, not a later live listing. It checks the actual private marker against that identity and copies only referenced `objects/<source-id>` through directory-handle-anchored/no-follow operations. Source size, SHA-256, ownership/mode/link count and identity/timestamps must remain valid; destination bytes are read back and checked after sync. Copy/hash loops use a 64 KiB buffer. Marker stability is rechecked across the copy. No `MediaFiles` initialization, source mutation, extraction, format revalidation, hard-link pin or scratch/orphan scan occurs. A null SQL identity requires no sources and an absent/empty selected media directory; unrelated existing store contents are not adopted.

The current implementation has an important provable invariant: source rows and their fingerprints/store identity cannot be deleted or updated; objects are synced and published **before** their synchronous SQL admission, under the same gate used by orphan cleanup. Cleanup tests current references and never removes referenced objects, including rejected/failed sources. Therefore a committed source in this snapshot remains referenced in the current database for this schema; no full-export cleanup pause or hard-link pin is needed. Do not hard-link originals into the backup: the live store refuses unexpected multiple links.

This argument depends on actual source immutability, not the general claim that a current unreferenced object was never referenced by a snapshot. If a future feature permits source deletion, it must add snapshot-lifetime pinning or coordinated descriptor retention under the cleanup gate **before** removing that invariant. Missing/corrupt/replaced originals or an identity conflict fail the whole attempt; do not omit the source or publish a database-only success. A bounded retry starts a fresh coherent attempt. External tampering is not repaired automatically.

### Local publication

Each attempt exclusively creates `.capture-<UUID>` under the explicit output parent, with private request metadata and a separate `snapshot` child (`0700` directories, `0600` files). Only compiled table files and selected originals are written; all written files are verified and synced, and the manifest is written last. The parent accepts a joined successful child with a matching manifest digest before publication.

Publication uses one narrow built-in `bun:ffi` call to Linux `libc.so.6` `renameat2(...,RENAME_NOREPLACE)` with held directory FDs. It atomically moves the complete snapshot on the same filesystem without replacing an existing empty directory, file or symlink. This requires that native symbol/kernel/filesystem operation; unsupported publication fails closed, with no plain-rename or overwrite fallback. A failed rename may reuse an existing destination **only after streaming full-tree path/type/mode/link/count/hash equality against the validated staging tree**. Otherwise the existing entry is untouched and capture fails. Concurrent equal snapshots can therefore converge on one immutable directory without clobbering caller-owned entries.

Before the commit point, failure/cancellation removes only this attempt's provably owned scratch and leaves earlier snapshots/unrelated entries untouched. Directory FDs and process work are joined/closed. The no-replace rename is the commit point: a later abort does not delete a completed snapshot. A post-commit sync/cleanup failure can report failure while retaining that complete directory for inspection; it never rolls back by deleting a good snapshot. Last-good data is never replaced, repaired or pruned automatically. Crash-orphan scratch is not scavenged by this API. Local payloads contain no control/request files, locks, credentials or diagnostics. This is local capture publication, not an atomic transaction spanning a live SQL database and files, and not Git delivery.

## Git configuration and scheduling

The daemon parses optional server-only `THOUGHTLOOM_BACKUP_CONFIG` JSON. Absence leaves backup unconfigured; an empty value is invalid. Parsing alone has no Git, network or filesystem side effects. At runtime, a positive interval enables one initial backup after readiness and subsequent scheduled attempts; a null interval starts no automatic backup service/timer or backup filesystem/Git work. The manual command requires explicit configuration regardless of interval.

```json
{
  "repositoryUrl": "git@github.com:OWNER/thoughtloom-backups.git",
  "checkout": "/absolute/private/thoughtloom-backup-checkout",
  "branch": "backups",
  "intervalSeconds": 86400
}
```

All four fields are required; extra fields are rejected. `intervalSeconds:null` disables automatic attempts; a positive safe integer specifies their interval in seconds. Daily is an example, not an enabled default. The absolute `checkout` must be lexically disjoint from the application, database and media paths. Whole attempts additionally check physical source/workspace separation, ownership and recorded identities as described below. Branches use Git ref naming rules; remotes are restricted to conventional SSH/HTTPS syntax, with no passwords, HTTPS userinfo, query strings, fragments or helper transports. SSH usernames are permitted; do not put tokens in URLs. Invalid settings produce categorized diagnostics without raw values. Test-only local remotes require a separate explicit delivery-test boundary and are not accepted by this parser.

Use the operator's SSH agent or host credential helper with noninteractive authentication. No token variable, browser credential, `.env` reader or credential in a snapshot/command example is required. Large original files can exceed a host's ordinary Git object/push limits: report delivery refusal and retain the local snapshot; do not silently drop files, introduce LFS or claim remote protection. A private Git repository is not an independent offline/encrypted backup.

### Internal delivery and checkout control

[`deliverBackup(options, dependencies?)`](../src/backup/git.ts) accepts a completed capture result, the validated `BackupConfig`, and optional `signal`/instance `logger`. It returns `{localCommit,remoteConfirmed}`. Offline, divergent or unconfirmed remote delivery retains the complete local commit and returns `remoteConfirmed:false`; unsafe inputs/checkouts and local preparation failures reject with categorized errors. Explicit cancellation rejects, retaining any already completed commit. A total deadline reached during remote delivery can return an unconfirmed local commit. The configured scheduler and manual command invoke it through the whole-attempt service below, not a daemon route.

The checkout must be absent, or have the matching tool-owned record. An arbitrary existing directory/repository, even an empty manually created directory, is not adopted. Its parent must exist, be canonical and owned/non-other-writable; the checkout and sibling control directory are private `0700` on the same supported local filesystem. Paths cannot contain symlink components or overlap the selected snapshot. Held directory identities guard the checkout, control and Git directories; payload files are private regular single-link files. Standalone delivery only receives the snapshot, not a database/media capability. The source-aware whole-attempt service below checks those additional physical boundaries; standalone consumers must not infer them from delivery alone.

For checkout `/private/backups/checkout`, control lives at `/private/backups/.checkout.thoughtloom-backup/`, outside the Git worktree and payload:

- `operation.lock`: a stable private inode held with Linux `flock(LOCK_EX|LOCK_NB)`. Close/process exit releases it; never unlink it to break contention. Acquisition polls asynchronously for at most 10 seconds.
- `state.json`: a bounded, atomically replaced/synced record of remote, branch, checkout device/inode, local-config fingerprint, completed HEAD/manifest and at most one pending adoption/update.
- `next` and `previous`: at most one complete staged replacement and its recorded preceding tree during an update. Only verified tool-owned preceding trees are removed after a completed commit; Git history is not deleted. `empty-template` prevents host Git templates being installed.

Standalone delivery acquires/releases its lease. Whole attempts use the exported `BackupCheckoutLease.acquire(config, signal?)` **before capture**, pass that same lease as `dependencies.lease` to delivery, and await `lease.release()` in the owner's `finally`. Delivery neither releases a supplied lease nor reacquires its lock, and refuses overlapping delivery use of that capability. This is a destination lock, not the daemon execution lease.

Delivery validates the canonical manifest/digest, compiled table-name set and closed filesystem membership, then streams file lengths/SHA-256 and Git blob identities. The shared [`snapshot.ts`](../src/backup/snapshot.ts) owns this file verification; the Git adapter retains its command/tree checks and error mapping. Delivery copies into new private files without hard links, reads the staged payload back, and never stages source paths or caller-owned leftovers. It does not invoke table decoding or SQL relationship validation merely because staging uses the same file verifier. Only `snapshot/` is passed to `git add --all -- snapshot`, after that tree's full allowlist is verified. The index and committed Git tree must exactly match its regular-file entries. Fixed content-free commit metadata contains the manifest digest; unchanged bytes create no commit, but still attempt pending remote delivery.

A pending update is recorded **before** moving the worktree. Resume accepts only recorded before/after manifest fingerprints, an index equal to the whole before or after tree, and HEAD equal to the preceding commit or the exact intended single-parent commit. Unknown edits are refused, not reset. Crash windows before a complete transition record, partial remote checkout, leftover Git lock files or ambiguous record writes may require operator inspection; they are not auto-cleaned. Complete snapshots/commits remain retained. Do not remove unknown artifacts to force a retry. Stale private `.state-<UUID>` temporary records from interrupted atomic writes are outside the payload and are not automatically scavenged.

A fresh checkout can adopt the configured existing branch only when its tip contains exactly the supported `snapshot/` payload with no extra tracked files, links or submodules. It checks manifest/tree paths before recording a pending adoption, then verifies materialized bytes before recording completion. A reachable remote with other branches but no configured branch is not treated as an empty dedicated destination. An initially unreachable remote can still leave a new local root commit; later unrelated remote history is a conflict, not permission to merge or overwrite it. Pushes are ordinary non-force pushes to the explicit configured branch. An advertised remote tip must be absent or an ancestor of the local commit. A subsequent `ls-remote` observation of the exact local OID confirms delivery, including after an uncertain push acknowledgement; exit status alone does not. Confirmation is an observation, not a promise that another operator cannot later change the branch.

The default runner requires Linux, `libc.so.6` `flock`/`renameat2`, `/usr/bin/git` **2.36 or newer**, and `/usr/bin/ssh` for SSH remotes. It currently creates SHA-1-format repositories; other object formats are refused. Each command has a 60-second deadline and at most 8 MiB combined stdout/stderr; one delivery has a 300-second cancellation budget. Manifest parsing is capped at 16 MiB (remote command output has its smaller bound). These are refusal budgets, not truncation or measured capacity/performance guarantees; Git has no separate RSS ceiling here. Copy/hash loops use 64 KiB buffers. The runner owns a detached process group, kills remaining ordinary Git/SSH/helper group members on exit/cancellation, closes/joins pipes and awaits Git exit. This is not containment of arbitrary hostile helpers that deliberately detach; uninterruptible OS I/O and parent death/power loss are not bounded-cleanup proofs.

Git receives exact argv and an explicit Git/worktree path, never shell interpolation. Client-side hooks, fsmonitor, automatic signing/maintenance, external diffs/text conversion, filters, attributes-based encoding/newline conversion and submodule recursion are disabled; replace refs, linked/shared object stores and unexpected refs/index states are refused. `core.fsync=all`/`fsync` requests Git durability. The default transport permits only HTTPS/SSH, with prompts disabled, SSH batch mode/strict known-host checking and a 15-second connection timeout. Host global/system configuration remains available for credential helpers, but no application/provider environment or `.env` is loaded: the child receives host PATH/HOME/XDG/keyring/SSH-agent, proxy and certificate-location values only, plus fixed noninteractive Git settings. Host credential helpers and SSH configuration are intentionally trusted authentication tools, not payload code. Raw output, URLs, paths, credentials and thought content are never logged.

The optional `dependencies.runGit` is a trusted owned-process boundary, used by isolated tests to redirect a validated HTTPS fixture URL to a local bare repository. It must honor the supplied cancellation signal and join its own resources; the default runner's process-group/environment enforcement does not apply to a replacement runner. No local URL or bypass switch is added to production configuration.

### Whole attempts and persistent capture workspace

[`runBackupAttempt(options, dependencies?)`](../src/backup/run.ts) takes canonical absolute `databasePath`/`mediaDirectory`, `BackupConfig`, optional `signal` and instance `logger`; it needs no daemon role credentials or OpenCode configuration. Its result is `{snapshot,localCommit,remoteConfirmed}`. Readonly preflight precedes acquiring the shared checkout lease; **capture cannot begin while another process owns that lease**. The lease remains held through capture, delivery and entered-resource cleanup. Existing capture/worker budgets and Git process deadlines apply unchanged. Optional `dependencies.runGit` has the same trusted owned-process responsibility as delivery's runner.

For checkout `/private/backups/checkout`, completed captures persist under `/private/backups/.checkout.thoughtloom-captures/`, separate from both `checkout/` and `.checkout.thoughtloom-backup/`. Each child is `snapshot-<manifestSha256>` with the capture layout above. Unchanged state reuses the verified same-hash directory, and unchanged Git content still retries pending delivery. A changed snapshot can append a local commit while retaining earlier pending commits in its ancestry. A capture failure ends that attempt before delivery; previously completed captures and pending commits remain for a later attempt. Neither success nor failure prunes completed captures or Git history.

The single [`BackupWorkspace` capability](../src/backup/workspace.ts) checks canonical paths, owner/mode and device/inode ancestry against the application, database and media roots before creating backup directories, and rechecks source/workspace identities across the operation. A read-only database descriptor retains its inode identity without starting another SQL transaction. The checkout, control and capture roots must not alias or contain one another or live sources. This does not acquire a source execution lease, migrate data, initialize a media store or modify business records.

An exclusively created empty private capture parent is bound by `.checkout.thoughtloom-backup/capture-workspace.json`: a private, synced, immutable per-workspace record, capped at 32 KiB, containing version `1`, checkout/remote/branch, capture path/device/inode, source database path/device/inode and selected media path. Existing roots without the matching record, missing/replaced roots, symlinks, unsafe modes, changed source bindings and unexpected root entries are refused without adoption or chmod/cleanup. Media-root identity is held for each attempt; capture still checks its SQL store ID and original fingerprints. Intentionally changing database identity requires a distinct configured checkout rather than rewriting this record.

The capture parent admits only private same-filesystem `snapshot-<64 lowercase hex>` directories. Older unselected snapshots are structurally checked, not fully rehashed on every tick; capture reuse and selected Git input receive full file verification. Interrupted initialization, malformed ownership records, unknown entries or crash-left `.capture-<UUID>` staging are preserved and block further automatic mutation for operator inspection. The service never deletes unknown artifacts or treats their presence as a held OS lock. Snapshot/control paths and source identities remain outside the portable payload and diagnostics.

### Configured scheduling and manual command

With a positive interval, [`BackupScheduler`](../src/backup/scheduler.ts) starts exactly one attempt **after migration, listener creation and the successful daemon-readiness event**, without delaying readiness until backup completes. One active attempt and at most one pending wake are retained. Ticks while work is held coalesce into one follow-up; delayed callbacks skip missed deadlines rather than replaying every missed tick. Ordinary attempt failure is logged safely and leaves the daemon and later scheduled wakes running. No configuration, or a null interval, creates no backup scheduler/timer or backup filesystem/Git work; the optional owned runtime timer/attempt seam is ignored in both cases.

The default technical clock is monotonic `process.hrtime.bigint()` expressed in milliseconds. Intervals and deadlines use bigint arithmetic, including every validated positive safe-integer seconds value. Individual `setTimeout` calls are chunked to at most `2147483647` milliseconds, never passed an overflowing/clamped delay. Scheduling state is process-local: restart begins one new attempt, not a persisted catch-up queue. Start/stop are idempotent; stop seals wakes, cancels the timer, aborts the entered attempt and **joins it**. Generation checks discard stale callbacks. Daemon shutdown joins backup capture/Git alongside its other producers before closing originals/database or releasing execution ownership. No snapshot or push is assumed successful merely because shutdown/timeout occurred.

The manual entry point, from the project root, is:

```sh
# Supply THOUGHTLOOM_DB_PATH, optional THOUGHTLOOM_MEDIA_DIR and
# THOUGHTLOOM_BACKUP_CONFIG explicitly in the launching environment.
bun --no-env-file scripts/backup.ts
```

It calls the same whole-attempt service as the scheduler, needs only backup configuration and database/media paths (not daemon user/AI roles or OpenCode configuration), and does not acquire the daemon's exclusive execution lease to read the source. It uses the supplied environment without loading dotenv files; `--no-env-file` also prevents Bun from loading them. SIGINT/SIGTERM abort the attempt and wait for cleanup. Optional `THOUGHTLOOM_LOG_LEVEL` follows daemon logging levels.

- The manual command retains whole-attempt locking across **capture and delivery**, including contention with the daemon scheduler.
- Retained local snapshots/commits retry idempotently on the next configured attempt or manual invocation; remote conflicts block delivery, not ordinary application use. Never reset local commits, auto-merge external edits, force-push, rewrite/delete remote history or prune it automatically.

Report **local snapshot**, **local Git commit** and **remote branch confirmation** separately. The manual command exits nonzero unless configured delivery is confirmed, even when local recovery data was saved. Info logs report completed changes/delivery; Warning reports recoverable/offline delivery and conflicts; Error reports terminal capture/configuration failure; Verbose handles command/poll/no-op detail. Log attempt/outcome and safe counts/digests, never private payloads or raw exceptions. Last-good local/remote status and retry bookkeeping stay outside the snapshot. Never reset local commits, auto-merge external edits, force-push, rewrite/delete remote history or prune history automatically.

## Offline restore and inert historical work

### Implemented private staging, not an installation

[`stageRestoreSnapshot(options)`](../src/backup/restore-staging.ts) is an internal API over an already selected snapshot. Required absolute canonical paths are `snapshotDirectory` and an existing private `stagingParentDirectory`; optional fields are `expectedManifestSha256`, `signal`, an instance `logger` and partial `limits`. The parent may contain caller-owned entries and must be outside Git and not inside the selected snapshot. The API creates only a fresh `.restore-<UUID>` child with `0700` directories and `0600` files. The return value is `{stagingDirectory,databasePath,mediaDirectory,manifestSha256,dispose}`; paths inside it are `thoughtloom.sqlite` and `thoughtloom.sqlite.media` with `objects`, empty `staging` and empty `prepared` directories. No existing workspace is adopted or overwritten.

`stageRestoreSnapshot` creates/syncs `.restore-in-progress` **before the database**, and leaves it present on success. This initial stage preserves the selected snapshot's original statuses, generations, cancellation facts and existing fence records exactly: staging alone applies **no recovery transitions or new fences**. The returned database is closed and is deliberately refused by normal startup. Do not remove its marker to start it. Staging itself has no target-publication argument, execution-owner registration, daemon/native startup or Git operation; the whole restore service below owns final installation.

The limits default to 16 MiB of manifest JSON, 64 MiB per table JSON and 256 MiB aggregate manifest/table JSON. Overrides must be positive safe integers. Limits are checked against lengths before table allocation; canonical parsing and decoded rows still consume additional memory. Originals are streamed with a 64 KiB buffer and are not limited by today's upload setting. Cancellation is cooperative around reads/copies and SQL boundaries; synchronous JSON/SQL work is not preempted. These are input bounds, **not hard RSS, CPU/deadline or daemon-latency guarantees**.

The loader migrates only its newly created empty database, captures application-generated schema/trigger definitions from that private database, and performs one guarded load transaction with foreign keys enabled/deferred and CHECK/UNIQUE constraints retained. Application triggers are temporarily removed there so seals, later title edits, cyclic media/import associations and exact run steps can be loaded without re-admission or automatic step-zero insertion. It removes only empty-migration seed records, inserts compiled columns with raw bound values, restores sequence high-water values, rebuilds derived FTS/spelling state/statistics without advancing plural search epochs, and reinstalls/verifies the original application guards. It never runs migration over loaded records or accepts payload DDL. Shared [`records.ts`](../src/backup/records.ts) checks are used by capture and staging without making WAL a staging requirement. Loaded rows are re-encoded and compared against every selected table's count/length/hash; media membership, SQL fingerprints, canonical marker and copied original bytes must also agree. Hashes detect corruption, not authenticity of the selected revision.

`dispose()` is an idempotent ownership capability. It first checks complete membership and recorded file/directory identities; unknown, changed or replaced entries cause `cleanup-conflict` and are preserved. Cleanup never removes caller-parent entries, and removes the marker only after the historical database and other staged payloads. Failure closes/rolls back entered resources and attempts only verified owned cleanup; ambiguous artifacts remain for inspection. Errors contain only a sanitized code: `invalid-snapshot`, `invalid-records`, `unsafe-path`, `aborted`, `storage-failed` or `cleanup-conflict`. Logs contain attempts/outcomes, counts and digests, not payloads or raw exceptions. Source-copy/inode races, close faults and arbitrary crash/power-loss behavior still require their separate validation controls.

### Implemented staged recovery transitions

[`recoverRestoreStage(stage, options)`](../src/backup/restore-staging.ts) is the explicit next internal operation on the **actual same-process capability** returned by `stageRestoreSnapshot`. It does not adopt a directory, accept reconstructed path objects or reopen crash-orphan stages. `options.restoredAt` is a required canonical UTC timestamp (`YYYY-MM-DDTHH:mm:ss.sssZ`); `signal` and instance `logger` are optional. The frozen result is `{manifestSha256,restoredAt,addedFences,interruptedRuns,interruptedImportFiles,invalidatedComposers}`. The digest always identifies the original selected snapshot, not a new payload containing the recovery changes.

Recovery verifies the owned workspace and original record fingerprints, then uses one immediate transaction on the existing staged DB, with exact integers, foreign keys, recursive triggers and the application's full guards retained. It never migrates that populated database or drops guards. The trusted [`restore-recovery.ts`](../src/backup/restore-recovery.ts) plans every missing fence and permitted raw-row change before issuing writes. All 41 tables and sequence values are checked afterward against the original plus exactly that plan; schema/guard definitions, shared record/range invariants and relationships must still hold before commit. Native facts, cancellation states, accepted payloads, original media, existing fences and unrelated records are unchanged. The transitions and before-value format are specified below.

An active search generation must be below `9007199254740991` before its required increment; another active run's generation must be below `9223372036854775807`. An increment beyond either applicable range refuses the whole transaction as `invalid-records`, rather than wrapping, saturating or skipping interruption. Terminal generations remain unchanged, including their permitted maxima. The Verbose `[restore] recovery validated` event occurs after delta validation but before the final cancellation check/commit; it does not itself report committed success.

Concurrent recovery entry is refused. Disposal seals further entry and joins entered recovery before inspecting/removing anything. After successful close/verification, the owner records the authorized DB fingerprint so the recovered stage remains disposable; a same-timestamp repeat verifies workspace ownership and returns the recorded result without another transition. A different timestamp is refused. Pre-commit failure/cancellation rolls back and revalidates the original state before authorizing disposal or retry. Ambiguous commit/close/artifact failures remain fail-closed behind the marker; disposal closes held handles but never deletes an ambiguously changed stage. Cancellation after a successful commit does not undo or reapply it.

The startup marker is left byte-for-byte unchanged, and the database is closed on return. This API performs no target publication, execution-owner registration, native call, daemon startup or CLI operation. Even a recovered stage is **not yet a published restore destination**: do not clear its marker to start it. Final lease/publication/startup evidence remains separate.

### Standalone offline restore

The [`restore command`](../scripts/restore.ts) consumes an **already selected** snapshot directory. It does not fetch, check out a remote revision, run repository scripts, connect to OpenCode or start the daemon.

```sh
bun --no-env-file scripts/restore.ts \
  --snapshot /absolute/trusted-selected-checkout/snapshot \
  --target /absolute/empty/recovered-thoughtloom
```

The target is a new/empty private restore destination containing `thoughtloom.sqlite` and `thoughtloom.sqlite.media`; the normal default media-path rule then works. Arbitrary split destinations are not needed for version 1. Refuse a nonempty target, existing populated database, existing media store, unsafe paths or an active target execution owner. There is no `--force`, merge, overwrite or in-place repair mode. Stop the target daemon explicitly; the command never stops it or the operator service. Configure fresh role credentials, agent settings and backup destination separately after recovery.

Both flags are required exactly once, with absolute paths; optional `--manifest-sha256 <64-lowercase-hex>` checks the selected manifest digest, not its authenticity. Unknown/duplicate flags, positional arguments and relative paths are refused. Only optional `THOUGHTLOOM_LOG_LEVEL` is read from configuration: no daemon roles, backup/agent settings or credential variables are required. Neither the import-safe `runRestoreCommand(args, env, deps?)` nor its entry point reads dotenv files; use `--no-env-file` to prevent Bun doing so. The main entry handles SIGINT/SIGTERM by aborting and awaiting entered work. Exit zero means confirmed restoration; failure/cancellation/uncertain publication is nonzero. Final command/restore logs contain digest/time, not private paths or payloads.

The internal [`restoreBackup(options)`](../src/backup/restore-staging.ts) takes `snapshotDirectory`, `targetDirectory`, explicit canonical UTC `restoredAt`, and optional `expectedManifestSha256`, `signal`, instance `logger` and the existing JSON `limits`. Its frozen result is `{targetDirectory,databasePath,mediaDirectory,manifestSha256,restoredAt}`. It owns staging/recovery and target publication; callers receive no raw ownership handles. Parsing/resource limits remain the staging limits above, not hard RSS/deadline or arbitrary OS-I/O cleanup guarantees.

The target parent must already exist, be canonical, owned by the current UID, non-group/world-writable, on a supported local Linux filesystem and outside Git. Existing targets must be private `0700` directories and empty; new targets are created privately only after staging/recovery succeeds. Target and selected snapshot/stage roots cannot overlap, including checked device/inode ancestry. The service creates external private scratch at `<target-parent>/.restore-work-<UUID>/`, containing the ordinary `.restore-<UUID>` stage. It never stages inside the selected backup or final target. Only verified owned scratch is removed; unknown artifacts remain for inspection. A scratch-cleanup conflict after confirmed restoration warns without deleting the completed target.

An existing directory containing only a zero-byte `thoughtloom.sqlite` and its private `thoughtloom.sqlite.execution-owner.sqlite` sidecar, optionally with the exact private sidecar companion `thoughtloom.sqlite.execution-owner.sqlite-journal`, is **not adopted**. After validating regular-file ownership, modes, single links, identities and exact directory membership, a read-only sidecar lock check may classify it as `target-busy`; an unheld candidate is still `target-not-empty`. The check uses a SQLite-managed read-only connection with before/after sidecar metadata checks, not an independent raw sidecar descriptor that could release a same-process owner's POSIX locks when closed. Other occupied destinations are refused without opening their database. This exception recognizes actual ownership contention without turning an empty placeholder into overwrite authorization.

### Validation and publication

1. Validate manifest/version/schema, canonical JSON/closed shapes, scalar encodings, unique identities, complete table/file membership, sequence high-water values and all lengths/hashes before touching application data. Validate actual references, including polymorphic exposure/dependency references, ordered maps/seals and source fingerprints; preserve supported legacy null/unknown facts rather than manufacturing evidence. Reject missing/extra/duplicate files, unsafe IDs/paths, absolute or traversal paths, NULs, symlinks and special/hard-linked payload files. Never open a path from a filename, import locator, binding or old prompt. Enforce bounded parsing/resources with safe errors, not payload excerpts.
2. Build and verify the load in private staging using only compiled application DDL/column mappings and parameter binding. Normal creation/admission APIs are inappropriate: they mint identities, schedule work and enforce initial-only conditions against later title metadata. Use an offline-only trusted loader, explicit transaction/rollback and deferred FKs for cycles. Install/verify the application's full guards after the load; disable no checks on a live application connection. No arbitrary schema/trigger text is accepted from the backup. Rebuild the two FTS projections (including media clarification, not filenames/binary text), spelling epoch and statistics only; preserve plural search epochs and recorded sequence high-water values. Validate FK/integrity checks and domain invariants before publication.
3. Reserve/check the empty target, exclusively create its empty DB/sidecar control files, and acquire its actual `ExecutionOwnerLease` on that final DB path. Recheck membership and the empty DB under ownership; an already-running contender must win or lose the same lease, not an unrelated sentinel lock. Control reservation necessarily precedes the marker. Do not replace the leased DB inode or sidecar, including by renaming a staging DB over it or copying/truncating file bytes into it. Before any schema/media/restored-data writes, durably create/sync `.restore-in-progress` and its directory. Daemon startup refuses any marker entry under its lease **before opening the knowledge DB, WAL setup, migration, workers or cleanup**, and fails closed on inspection errors. It neither follows nor removes the entry.
4. Under that lease, stream verified originals into a newly created private media layout with the original SQL store identity/canonical marker and empty scratch directories. The shared trusted [`restore-load.ts`](../src/backup/restore-load.ts) bootstraps only the empty target and transactionally loads the already recovered raw records on its fixed inode. It uses application DDL and controlled guard suppression/reinstallation, not payload SQL or ordinary admission. Fences/transitions are copied exactly from the verified recovered stage, **not applied twice**. Recheck all 41 tables, sequences, guards, relationships, media bytes and derived projections. Do not register the installer's new owner in historical records; normal later startup registers its own owner.
5. Commit, close/check the target DB, sync files/directories, then remove the marker and sync its directory **last**. Release ownership and close entered target resources before confirmed success. This is fail-closed logical publication across SQL and files, not a fictitious atomic rename of two resources. Preexisting occupied destinations are untouched. Before the marker, failure can leave only reservation controls; after the marker but before publication, entered SQL rolls back where possible and partial target files remain marker-gated. No failed target is automatically deleted, repaired, adopted or retried. Never remove a last-good backup or clear a marker to force readiness.

After actual lease acquisition, an optional exact sidecar journal is pinned and checked separately as live lease control data: it must remain a private, regular, single-link file on the same inode, but its contents and modification times are not immutable payload. It is not copied, rewritten, explicitly synced or removed by restore; SQLite owns its lifecycle, including removal on lease release. No arbitrary journal/WAL/SHM names or other extra entries are allowed by this exception.

The verified sidecar descriptor is retained and reused for syncing, never transiently opened/closed under the lease. Cleanup releases the actual SQLite lease before closing that descriptor, including after pinning, verification or sync errors. If lease release cannot be confirmed, the owner and descriptor remain retained until process exit instead of risking premature lock release; the operation fails as `storage-failed`, or `publication-uncertain` once publication has been entered. Journal disappearance while ownership is required still refuses the restore; it is not accepted as a substitute for preserving exclusion.

The Info boundaries are `[restore] target ownership acquired` (fixed empty DB, no marker yet), `target marker durable` (before schema/media writes), `target database committed` (not yet published) and `target validated` (before the final cancellation/publication check), each with the `[restore] ` prefix. They are synchronous logger events over real phases, not fake readiness. The final `[restore] installation succeeded` follows marker removal/sync and lease release; that existing log name means the destination's files were restored, not packages or services installed. Cancellation after the publication boundary cannot undo a confirmed restoration.

Marker unlink followed by directory-sync failure cannot guarantee the marker remains. On that failure, while still holding target ownership, the service attempts one safe marker reinstatement/sync without overwriting an unknown entry. It reports `publication-uncertain` if publication cannot be confirmed; target-close or final ownership-release failures after publication also use that category and may leave the marker absent. Preserve the target for inspection: a nonzero result does not prove no destination data was written. Other safe categories are the staging codes plus `target-not-empty` and `target-busy`. Power loss, hostile path replacement and faulted OS I/O require their separate validation; this API provides no automatic crash-orphan resume.

### Small durable guard, not a second execution engine

The additive [`restore_fences` table](../src/storage/restore-fences-schema.ts), **entity-authority/coordination guards**, preservation of existing fences, staged recovery transitions and offline installation are implemented. Its primary key is `(entity_kind,entity_id)`, followed by `snapshot_sha256`, `restored_at` and `original_state_json`; all columns are non-null TEXT. Kinds are `run`, `import-batch`, `import-file` and `composer`. SQL requires nonempty identity/time, a lowercase 64-character hex digest and JSON-object original state; update/delete/replacement guards protect records. Migration creates no fence records. Staged recovery supplies the selected manifest digest and UTC restoration timestamp, and stores exact original mutable fields that recovery changes in each new fence, using the scalar encoding above inside canonical `original_state_json`: keys are qualified column names such as `runs.status`, `runs.generation`, `search_turns.open_slot`, `markdown_import_files.outcome`, `markdown_import_files.reason_code` and `search_composer_contexts.state`. Keys are sorted in ASCII order, integer values retain their tagged decimal encoding, and the JSON text ends with LF. The search slot before-value belongs to its run's fence. Use `{}\n` when no fields changed. Rows have no liveness/release flag and no FK that loses the fence when search content is purged. There is no unfence/reactivate command in this scope. Existing fences are retained verbatim on a later restore, even if that identity still needs a local transition; add fences only for newly encountered identities, never amend earlier provenance.

The implemented [`shared guard`](../src/storage/restore-fences.ts) consults each entity kind directly; a run fence needs no live `runs` row. Migration and execution checks refuse unavailable/incompatible compiled fence-table or immutable-trigger definitions. Existing claim/context/dispatcher transactions check before returning cached capability results or receipts; preparation, binding, legacy writes, run finalization and ordinary cancellation settlement also refuse fenced authority. Direct normal-worker ticks check before binding selection/discovery and native work, including their terminal/purged cleanup tail; configured transport resolution rechecks around its await. Run Stop is an idempotent control read for fenced identities: it does not change status, generation, steps, bindings, receipts or cancellation evidence. History/receipt/binding inspection remains available, and unfenced identities retain their existing authority rules.

Import authority checks the associated batch, file and run. A fenced batch rejects new file keys as closed admission, while exact batch/file receipt replay remains historical; sealing returns its stored state without inventing a timestamp. Direct claims, private/prepared input, partition choice, finalization, failure, Stop and cancellation settlement cannot execute or delete payloads for a fenced owner. Configured and configless scans exclude those owners before their work limits; waiter promotion and local settlement repeat the authority checks or apply the same transactional SQL exclusion. Accepted SQL payloads remain retained. Existing canonical document/namespace reuse is unchanged.

A fenced composer cannot extend/refresh its ledger or authorize/consume a new turn, even with a valid old token. Existing turn-key replay resolves first, and the saved session itself is not fenced: a fresh composer can authorize fresh work under ordinary rules. Retained and purged search-cleanup authority checks the run fence before preparation, drain qualification, admission/observation merging, native cancellation or any certificate/settlement write, including when given an identity cached before fencing. Controller-backed local Delete skips native proofs and new cleanup seals for fenced runs, preserves any existing cleanup row and the fences, and applies the normal proof/cleanup rules to fresh runs in the same session. Rejection invalidation skips historical fenced run/composer journals while retaining current source eligibility checks.

Execution authority for every entity kind also requires identity-consistent binding: after exact fence detection, the guard compares the supplied ID's UTF-8 bytes with its actual ordinary SQLite string-binding bytes. A mismatch (including a leading-BOM alias on affected runtimes) is refused before downstream authority, cached replay or discovery, not silently redirected to another entity. Exact historical fence lookup still works without an entity row. This conservative refusal does not add execution support for unusual historical IDs or rewrite IDs, native facts, content or backup bytes; ordinary history readers are unchanged.

Fence **every restored run ID**, including terminal runs and IDs present only in `search_native_cleanup`; every restored import batch/file; and every restored composer. This is a finite historical identity set. It does not disable new work globally or infer a cutoff from reusable rowids, timestamps, PIDs or remote availability.

Staged recovery performs only these local recovery transitions; retain their before-values in each newly added fence record:

| Snapshotted state | Restored local treatment |
| --- | --- |
| Run `queued`, `submitting`, `running` or `uncertain` | Set local status to `interrupted` and increment generation once, checked without overflow. **Do not change cancellation state or any `run_steps` field.** Search's slot closes consistently with the interrupted run; retain any existing outcome reason, and leave an absent reason null rather than inventing user Stop. |
| Terminal run (`completed`, `failed`, `interrupted`) | Preserve status/generation and cancellation state. A completed native step without local finalization stays historical; never finalize it during restore/startup. |
| Pending import holder or waiter (`outcome` null) | Set local file outcome/reason to `interrupted`/`interrupted`, retaining its IDs, run/waiter links, digest and any SQL payload. This releases pending-holder reservations and prevents waiters from acquiring new runs. It is recovery interruption, not proof the user pressed Stop. Do not create a document, choose a new partition or delete accepted bytes. |
| Terminal import receipt; open/sealed batch | Preserve terminal facts and existing sealing time/null. All restored batches are closed to **new** file admissions by their fence; exact request-key replay remains historical. Do not invent a sealing timestamp. New imports use a new batch/key. |
| Active composer | Set state to `invalidated`, preserving revision and complete dependency ledger. Other composer states remain unchanged. Old tokens cannot authorize a new turn. |
| Cleanup row, binding, step, receipt, draft, response or confirmed output | Preserve exact recorded facts. Do not rewrite paths, native IDs, inputs, permission bindings, envelopes/results, ownership manifests or terminal/drain evidence. Do not turn a draft into a canonical reply. |

The implemented fences are in existing trusted storage/worker boundaries, **not only in scanner queries**. They deny claim/recovery, preparation/binding, service resolution, native submission/observation/cancellation/Stop side effects, cached capability replay, knowledge writes, import local finalization and automatic cancellation settlement for restored identities. Configless import/waiter scans and purged-cleanup storage paths honor the same authority. A Stop of fenced history is a local idempotent control read, never a call to the old service. Retained cancellation `pending` stays pending; `none` is not upgraded to a never-submitted certificate, and an old `settled` value is not newly certified. The offline restore command itself makes **zero** native calls.

Live weave subject/eligibility/dispatch exclusion considers only unfenced work, including when an old journal retains unresolved submission evidence. Supervisor run and purged-cleanup scans exclude fenced IDs before their capacity limit. Historical/latest-run and by-key inspection remain available; scheduling filters do not remove old user receipts. A fence separates installations, **not a claim that old remote work has ended**. New explicit user actions may admit fresh identities/bindings using newly configured current paths and normal rejection/permission checks; same-key replay never allocates a replacement. No startup reweaving, title regeneration, import completion, native cleanup or response publication is authorized merely by restoring. Confirmed existing interpretations still prevent another initial media summary; deliberate Reinterpret/Evolve retains its ordinary distinction.

Authority guards do not perform recovery transitions as a side effect. The explicit staged recovery step closes restored search slots and interrupts pending import holders/waiters as specified above, releasing their existing SQL reservations. Inserting a fence alone is not a substitute for installing and validating that coherent restored state.

Normal saved-search reads, fresh composers/turns and deliberate local Delete remain available. Deleting a restored search session may purge its local content through the existing retention boundary while retaining the no-prose fences; it must not seal a fabricated new cancellation certificate or schedule old native cleanup. New unfenced runs retain ordinary Stop/recovery/cleanup semantics. Migration and backup must preserve fences, and startup must fail closed if their schema/required guards are unavailable. Running an older release that ignores these controls is unsupported.

**External effects are not rolled back.** The original installation or OpenCode may still have pending work; portable restore neither stops nor certifies it. Keep the original installation stopped and reconcile its external work separately before deliberately requesting new overlapping work. Unknown remote completion can remain unknown indefinitely without preventing unrelated new work in the recovered installation. This policy preserves history without reviving it; it is not native-session continuation at a new path.

## Required evidence before shipping

This document's source/official-document checks are design evidence, **not runtime proof**. The separate [validation boundary](testing.md#backup-and-recovery-validation) must establish:

- Compiled inventory versus a freshly migrated owned schema, FTS-shadow exclusions, exact INTEGER/BLOB/TEXT/BOM round trips, sequence high-water values and the listed rowid-dependent order.
- WAL read-snapshot coherence with concurrent HTTP/SQL mutations and file-first admission; bounded source-reader lifetime, memory and ordinary-write latency; fail-closed rollback-mode refusal. No live operator database or journal-mode experiment.
- Current immutable-source/cleanup reasoning exercised at held publication/copy/cleanup boundaries, including missing/corrupt files and a lowered current upload limit. Future source deletion cannot inherit this proof.
- Offline trusted loading of guarded cyclic/sealed records with later title edits, full rollback, marker/lease ordering, competing startup, interruption at each publication boundary and no overwrite of a nonempty target.
- Configured **and configless** normal startup, direct worker/Stop/cached-result paths, import holders/waiters and purged cleanup with native tripwires: no old service resolution, create, submit, observe or cancel calls; unchanged native/cancellation facts; fresh independent work still succeeds.
- Owned local/bare Git remotes: no-op commits, scheduled/manual overlap, pending delivery/restart, offline and uncertain pushes, divergence, unsafe paths/credentials/hooks and last-good preservation. No automatic destructive history operation.

Capture, Git delivery, whole attempts, manual invocation, daemon scheduling, entity/coordination fences, private staging/recovery, destination publication and the standalone command have separate focused validation boundaries. The [selected-revision walkthrough and synthetic measurement](testing.md#selected-revision-recovery-walkthrough) add composed recovery evidence; they do not establish every fault scenario above, hosted-Git compatibility, a hard memory bound or production capacity.
